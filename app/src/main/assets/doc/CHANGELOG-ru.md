# v1.0.1

###### 2026/09/21

* `Исправление` POP3 Outlook.com с токеном OAuth 2.0 (матрица провайдеров дорожной карты почты P6, 2026-09-21): сервер отвечает на однострочный `AUTH XOAUTH2 <base64>`, который Angus Mail шлет по умолчанию, `-ERR Protocol error. Connection is closed.` и разрывает соединение, поэтому учетная запись POP3 на предустановке `outlook` завершалась `AUTH_FAILED`; предустановки получили `pop3Xoauth2TwoLine` (каталог версии 3, true для `outlook` и `office365`), и ядро почты теперь шлет для этих предустановок и для любого хоста POP3 Microsoft, указанного без предустановки, сначала одну команду, а ответ base64 после продолжения `+` от сервера (`Pop3OAuthScriptedTest`, 5 случаев; проверено на реальной учетной записи в JVM и на устройстве API 33)
* `Улучшение` Столбец Outlook.com матрицы провайдеров (дорожная карта почты P6) и строки устройств P5 выполнены с токеном из регистрации публичного клиента Entra сопровождающего на одной личной учетной записи: проверка сессии, папки (роли по общепринятым именам, без SPECIAL-USE), отправка (`sentCopy = server`, Message-ID переписывается сервером), список (видно примерно через 7 с), серверный поиск (все ключи находят; китайская тема находится верно, но сервер тратит минуты на ящике из 2300 писем), тело, вложение, флаги (собственные ключевые слова не хранятся), создание папки, `MOVE`, наблюдение (IDLE уведомляет примерно через 10 с после отправки, быстрее всех семи провайдеров), POP3 (UIDL из 5 символов, только что отправленное письмо видно) и очистка (копии отправленного адресуемы по UID) проходят; на Redmi (API 33) сценарии baseline, остановка плагина и выключение Wi-Fi приходят за 9-14 с с теми же последовательностями событий, что и у Gmail; заметки предустановок, README и файлы свидетельств фиксируют отличия, включая отказ `535 5.7.139 SmtpClientAuthentication is disabled for the Mailbox`, который Microsoft выдает новым личным ящикам

* `Функция` Отслеживание новой почты через Binder (дорожная карта P5): `IMailSession.watch` открывает отслеживание поверх наблюдателя ядра почты и отвечает сразу (null с причиной в состоянии сеанса, если сеанс закрыт, достигнут `MAX_WATCHES_PER_SESSION`, параметры непригодны или обратный вызов хоста уже мёртв); события приходят в `oneway` обратный вызов хоста из потока доставки с `generation` хоста и `seq`, считаемым с 1, очередь из `MAX_WATCH_QUEUE` событий сворачивается в один `resync`, когда хост перестаёт их забирать, событие больше `MAX_ENVELOPE_BYTES` уходит без тела или как `resync`, `stop`, закрытие сеанса и смерть хоста завершают отслеживание одним событием `closed`, смена или потеря сети по умолчанию сразу переподключает работающие отслеживания, а возможности теперь объявляют `idle`

Сама матрица (QQ на эмуляторе API 24 и двух телефонах Sony, 163 на Redmi: убийство процесса плагина, потеря сети, переход с Wi-Fi на сотовую сеть, принудительный Doze) записана в `docs/dev/p5-watch-evidence.md` вместе со скриптом `docs/smoke/watch.js` и драйвером `.python/run_watch_matrix.py`; та же матрица показала, что Doze замораживает сеть фоновых приложений (повторные подключения отслеживания истекают по времени, а на Android 9 о новом письме сообщалось примерно через четыре минуты после пробуждения), поэтому плагин теперь переподключает свои отслеживания в момент выхода устройства из Doze, а подсказка об оптимизации батареи на странице настроек объясняет, для чего нужно исключение
* `Исправление` Матрица TLS (дорожная карта почты P6): неявный SSL, STARTTLS (через STARTTLS-прокси перед GreenMail), открытый текст, самоподписанный сертификат с `tls.trustAll` и без него, доверенный сертификат с несовпадающим именем хоста, неверный режим для порта и порт без предложения апгрейда теперь проверяются для IMAP, POP3 и SMTP (`TlsMatrixTest`, `docs/dev/p6-tls-matrix.md`); прогон показал, что хранилище POP3 в Angus сообщает об отсутствии STLS и о тайм-ауте приветствия как об ошибке аутентификации, и преобразователь ошибок теперь возвращает `TLS_FAILED` и `TIMEOUT` вместо `AUTH_FAILED`; `TlsDeviceTest` подтверждает на API 24, 28 и 33, что почтовое ядро с настройками платформы по умолчанию подключается к серверу только с TLS 1.2 и согласует TLS 1.3 начиная с API 29
* `Исправление` Матрица кодировок (дорожная карта почты P6): GB18030, GBK, GB2312, Big5, ISO-2022-JP, EUC-KR и UTF-8 в темах, отображаемых именах, телах и обеих формах имен файлов теперь проверяются объявленными, необъявленными и неверно объявленными (`CharsetMatrixTest`, `docs/dev/p6-charset-matrix.md`) и на API 24 / 28 / 33 (`CharsetDeviceTest`); прогон исправил два пробела декодирования: тело или заголовок, объявленные как `us-ascii` / ISO-8859-1, но несущие байты UTF-8 или GB 18030, выходили кракозябрами Latin-1 (Jakarta отображает `us-ascii` в никогда не отказывающую ISO-8859-1) и теперь идут через цепочку угадывания, а сырые темы и тела ISO-2022-JP без кодированного слова распознаются по управляющим последовательностям; Big5 и EUC-KR по-прежнему требуют объявления (их пары байтов допустимы и в GB 18030)
